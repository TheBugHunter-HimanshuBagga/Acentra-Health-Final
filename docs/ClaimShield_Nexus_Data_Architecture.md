# ClaimShield Nexus: Data Architecture

*Scope: the exact datasets, schema, ground truth, splits, generation and storage. Replaces the data sections of the earlier plan. Detection logic, scoring and UI are unchanged and live in the other two documents.*

**Honesty rules for this document**
- No public dataset used here contains FWA labels, ownership, referral networks, facility geography or investigation history. Every one of those is **generated by us** and is labelled synthetic everywhere it appears.
- CMS field names for the 2023 synthetic files **could not be verified** (data.cms.gov blocks automated access; ResDAC's pages list only general content areas: diagnosis, HCPCS, dates, charges, allowed/reimbursement amounts, provider NPI). That is why §1.3 defines an **adapter contract**, not field names. Anything marked **[verify]** is settled in hour 0 by opening the CMS data dictionary in a browser.
- Numbers like "~500 providers" are **design targets**, not facts about the data. §16 gives the rule for adjusting them after profiling.

## 1. Exact source datasets

### 1.1 What we load

| # | Source | Used for | Loaded tables | Link |
|---|---|---|---|---|
| S1 | **CMS Synthetic Medicare Enrollment, FFS Claims & PDE (2023 release)**: 8,671 synthetic beneficiaries | Members, professional (carrier) lines, DME lines, inpatient stays | `stg_cms_*` → `member`, `claim`, `claim_line`, `inpatient_stay` | [collection](https://data.cms.gov/collection/synthetic-medicare-enrollment-fee-for-service-claims-and-prescription-drug-event), [user guide](https://data.cms.gov/sites/default/files/2023-05/d51e1218-68c3-4c7c-9598-0b81f22fe903/User%20Guide%20-%20CMS%20Synthetic%20RIF%20Files%20May%202023_AM508_v2.pdf) |
| S2 | **CMS NCCI PTP edits, Practitioner** (latest listed: 2026 Q4, effective Oct 1 2026) | Real code pairs that must not be billed together | `ref_ncci_ptp` | [page](https://www.cms.gov/medicare-medicaid-coordination/national-correct-coding-initiative-ncci/ncci-medicare/medicare-ncci-procedure-procedure-ptp-edits) |
| S3 | **CMS NCCI MUE, Practitioner + DME** | Maximum units per code per day | `ref_mue` | [page](https://www.cms.gov/medicare-medicaid-coordination/national-correct-coding-initiative-ncci/ncci-medicare/medicare-ncci-medically-unlikely-edits) |
| S4 | **Fallback only:** CMS DE-SynPUF Sample 1 (Beneficiary + Carrier + Inpatient) | Used only if S1 cannot be mapped within 2 hours of hour 0 | same canonical tables via a second adapter | [Sample 1](https://www.cms.gov/Research-Statistics-Data-and-Systems/Downloadable-Public-Use-Files/SynPUFs/DESample01), [user document](https://cms.gov/Research-Statistics-Data-and-Systems/Downloadable-Public-Use-Files/SynPUFs/Downloads/SynPUF_DUG.pdf) |

### 1.2 What we do **not** load, and why
- **Pharmacy (PDE), SNF, home health, hospice, outpatient-facility claims.** No official FWA behaviour needs them, each adds a mapping risk, and `claim.claim_type` is an open enum so they can be added later. *Say this out loud in the demo*: "professional, DME and inpatient claims are implemented."
- **Real-provider datasets** (LEIE names, Medicare provider utilization by NPI). They would let a judge point at a real provider name on screen. Only the LEIE *column layout* is copied for the synthetic `exclusion` table.
- **Kaggle provider-fraud sets.** License and label provenance could not be verified.

### 1.3 Facts about S1 and S4 that shape the design
- S1 is described by CMS as "realistic-but-not-real" ([ResDAC](https://resdac.org/cms-public-use-files-for-researcher-use)). A third-party load reports 7 claim types, claims from late 2014 to early March 2023, carrier ≈ 1.12M rows (90.7k claims), DME ≈ 103.8k rows ([GitHub project](https://github.com/ameer0108-a/medicare-claims)). **Treat these counts as unverified; profile after download.** Early March 2023 as the end suggests the final month is partial, so the profiler drops it.
- S4's user document states provider identifiers were altered and assigned to beneficiaries **by geography only**, and dates were perturbed. Its carrier file has performing-physician NPI and tax number but, per the variable list, no referring/ordering NPI. So **provider behaviour in either CMS file carries no real signal**, which is why we do not trust it as provider identity (§11.3) and why our own overlay defines provider behaviour.

### 1.4 Adapter contract (the only source-specific code)
Each source adapter must produce `stg_line`, `stg_claim`, `stg_member`, `stg_stay` with these **required** fields. If any are absent in S1, the stated fallback applies; the canonical schema does not change.

| Canonical field | Meaning | If absent from the source |
|---|---|---|
| `src_bene_key` | Beneficiary identifier | **Hard requirement.** Switch to S4 |
| `src_claim_key`, `line_no` | Claim and line identity | Hard requirement |
| `service_from_dt`, `service_thru_dt` | Line dates of service | Hard requirement |
| `hcpcs`, `modifier1`, `modifier2`, `units` | Procedure, modifiers, service count | `modifier*` may be null; others hard requirements |
| `performing_npi` | Performing provider | Hard requirement (re-keyed immediately) |
| `line_allowed_amt` or `line_paid_amt` | Money | If only one exists, derive the other as 1:1 and record it in `gen_manifest` |
| `pos_code` | Place of service | Derive from claim type (carrier default `11`) and record it |
| `dx1..dx3` | Diagnoses | Optional; used only for `member.acuity_score` |
| `referring_npi` / `ordering_npi` (DME) | Referral source | **Expected to be absent.** Pseudo-referrals are generated (§11.5) and flagged in `gt_referral_origin` |
| `provider_specialty` | CMS specialty code | Infer from HCPCS family (§11.3) |
| `bene_death_dt`, `bene_state/county` | Member attributes | Death date: assigned by overlay. State/county: replaced by our synthetic geography anyway |

## 2. Exact synthetic datasets we generate

| Generated dataset | What it is | Target size (initial) |
|---|---|---|
| **Geography** | A fictional region: 3 regions × 4 counties, each with a centroid and a rural flag. Distances are Haversine on synthetic lat/lon. Not real addresses | 12 counties, ~700 addresses (+1 per member) |
| **Providers** | ~450 individual + ~50 organization providers, each with specialty, address, phone, TIN, enrollment date | ~500 |
| **Facilities** | Hospitals, clinics, DME warehouses, labs, dialysis-like centers | ~40 |
| **Owners / ownership** | Owner persons and holding companies with provider/facility ownership percentages | ~120 owners, ~250 links |
| **Referrals** | One row per referral/order edge, derived from CMS claims where possible, otherwise pseudo-assigned | one per DME claim + a sample of professional referrals |
| **Exclusions** | LEIE-shaped synthetic list | ~8 rows (2 live in schemes) |
| **Member attributes** | Synthetic address, acuity score, death dates for ~2.5% of members | per member |
| **Ghost members** | Members with no CMS source, used by phantom scheme PHC | ~100 |
| **Injected schemes (13 types, 36 instances)** | New and modified claim lines | ~55 providers touched |
| **Legitimate decoys (5 types, 14 instances)** | Behaviour that triggers detectors but is legitimate | 20 providers |
| **Prior investigations** | History with dispositions and rationales | ~100 |
| **Seed precedents** | One per closed investigation | ~100 |
| **Exception rules** | 1 pre-approved, others drafted live | 1 seeded |
| **Policy corpus** | Short synthetic policy sections the briefs cite | ~20 sections |
| **Ground truth** | Scheme, subject, line-level and prediction labels, kept in a separate database file | see §8 |

## 3. Storage choice (final)

| Store | Engine | Contents | Access |
|---|---|---|---|
| `data/claims.duckdb` | DuckDB | Schemas: `ref`, `core`, `feat`, `out` (reference, entities and claims, features, detector output) | Python read/write |
| **`data/gt.duckdb`** | DuckDB, **separate file** | All `gt_*` tables | Opened **only** by `predict/train.py`, `eval/`, and the exception `/simulate` backtest. Detectors never attach it. A unit test fails if any detector module imports the ground-truth path |
| `data/processed/*.parquet` | Parquet | Frozen snapshot of every canonical table, named by `master_seed` | Reproducibility and fast reload |
| `app.db` | SQLite (WAL) | `serving_*` (Python writes) and `wf_*` (Java writes) | As in the architecture document |
| `data/raw/` | Files | Downloaded CMS and NCCI files, **never committed to git** (NCCI sits behind an AMA license click-through) | Ingest only |

DuckDB is the analytical store because rules, peer statistics and backtests are set-based SQL over a few hundred thousand lines. SQLite is the workflow store because Java reads it and the demo needs one file.

## 4. Entity relationships (core)

```
address ◄──── member                      owner ──► ownership ──► provider
   ▲  ▲                                                  │            │
   │  └──── provider ──► provider_facility ◄── facility ─┘            │
   │          │ ▲                                  ▲                  │
   │          │ └─── referral (from → to, member) ─┼──────────────────┘
   │          ▼                                    │
   │       claim ──► claim_line ──► ref_hcpcs      │
   │          │ (billing / rendering / referring)  │
   │          ├──► member                          │
   │          └──► facility ───────────────────────┘
   │       inpatient_stay ──► member, facility, claim
   └── facility.address_id
exclusion ──► provider        investigation ──► investigation_provider ──► provider
                              precedent ──► investigation (nullable)
ref_ncci_ptp / ref_mue / ref_hcpcs  ← joined by HCPCS code only (no FK)
rule_registry ──► rule_policy ──► policy_section
exception_rule ──► precedent
```

Polymorphic references are avoided. `ownership` carries two nullable foreign keys with a CHECK that exactly one is set.

## 5. Reference and knowledge tables (`ref`, in DuckDB; copied to SQLite where the UI needs them)

```sql
CREATE TABLE ref_specialty (
  specialty_code VARCHAR PRIMARY KEY,         -- e.g. 'PRIMARY_CARE'
  name           VARCHAR NOT NULL,
  category       VARCHAR NOT NULL,            -- PROFESSIONAL | DME | ANCILLARY
  peer_group     VARCHAR NOT NULL             -- peer key; = specialty_code unless merged for small groups
);

CREATE TABLE ref_hcpcs (
  hcpcs              VARCHAR PRIMARY KEY,
  short_label        VARCHAR NOT NULL,        -- OUR short label; no AMA descriptors stored
  family             VARCHAR NOT NULL,        -- EM_OFFICE | EM_OTHER | PROCEDURE | IMAGING | LAB | THERAPY | DIALYSIS | INFUSION | DME
  em_level           TINYINT,                 -- 1..5 for office E&M families, else NULL
  typical_minutes    SMALLINT,                -- OUR demo assumption for time-based checks; NULL if untimed
  is_timed           BOOLEAN NOT NULL,
  reference_allowed  DECIMAL(10,2) NOT NULL,  -- median allowed amount for the code, computed from the loaded base data
  is_high_cost       BOOLEAN NOT NULL DEFAULT FALSE,   -- top decile of reference_allowed within DME family
  dme_category       VARCHAR
);   -- only codes present in the data or injected by us

CREATE TABLE ref_ncci_ptp (
  ptp_id        BIGINT PRIMARY KEY,
  col1_hcpcs    VARCHAR NOT NULL,
  col2_hcpcs    VARCHAR NOT NULL,
  modifier_ind  TINYINT NOT NULL,             -- 0 = never allowed together, 1 = allowed with an appropriate modifier, 9 = not applicable (per CMS definition; confirm on load)
  eff_dt        DATE NOT NULL,
  del_dt        DATE,
  source_file   VARCHAR NOT NULL,             -- file name + quarter, e.g. practitioner v?? 2026Q4
  UNIQUE (col1_hcpcs, col2_hcpcs, eff_dt)
);
-- Load only pairs where col1 or col2 appears in claim_line (keeps the table small).

CREATE TABLE ref_mue (
  hcpcs         VARCHAR NOT NULL,
  service_type  VARCHAR NOT NULL,             -- PRACTITIONER | DME
  mue_value     INTEGER NOT NULL,
  mai           TINYINT NOT NULL,             -- MUE adjudication indicator, as published
  PRIMARY KEY (hcpcs, service_type)
);

CREATE TABLE ref_place_of_service (
  pos_code    VARCHAR PRIMARY KEY,
  label       VARCHAR NOT NULL,
  is_facility BOOLEAN NOT NULL
);

CREATE TABLE ref_scheme_type (
  scheme_type        VARCHAR PRIMARY KEY,     -- DUP, UPC, UNB, EXU, PHA, PHB, PHC, TMA, TMB, UTL, DME, RNG, EXC
  official_category  VARCHAR NOT NULL,        -- DUPLICATE_BILLING | UPCODING | UNBUNDLING | PHANTOM_SERVICES | EXCESSIVE_UTILIZATION | IMPOSSIBLE_TIMING | COORDINATED_NETWORK | EXCLUDED_PROVIDER
  description        VARCHAR NOT NULL,
  severity_weight    DOUBLE NOT NULL,         -- 0..1 used in queue scoring
  harm_weight        DOUBLE NOT NULL,         -- 0..1 member-impact weight
  default_action     VARCHAR NOT NULL         -- must be in allowed_actions
);

CREATE TABLE ref_reason_code (
  reason_code VARCHAR PRIMARY KEY,
  applies_to  VARCHAR NOT NULL,               -- REVIEW | CLOSE | EXCEPTION
  label       VARCHAR NOT NULL
);

CREATE TABLE policy_section (
  section_id   VARCHAR PRIMARY KEY,           -- 'DME-POL-4.2'
  doc_id       VARCHAR NOT NULL,
  title        VARCHAR NOT NULL,
  body         VARCHAR NOT NULL,
  version      VARCHAR NOT NULL,
  eff_dt       DATE NOT NULL,
  provenance   VARCHAR NOT NULL DEFAULT 'SYNTHETIC: written for this demo, modeled on public CMS concepts'
);

CREATE TABLE rule_registry (
  rule_id        VARCHAR NOT NULL,            -- 'R-DUP-01'
  version        INTEGER NOT NULL,
  name           VARCHAR NOT NULL,
  scheme_type    VARCHAR NOT NULL REFERENCES ref_scheme_type(scheme_type),
  family         VARCHAR NOT NULL,            -- rule | stat | graph | temporal
  logic_ref      VARCHAR NOT NULL,            -- path of the SQL/function implementing it
  params_json    VARCHAR NOT NULL,            -- thresholds; tuned on train/val only
  status         VARCHAR NOT NULL,            -- ACTIVE | RETIRED
  PRIMARY KEY (rule_id, version)
);
CREATE TABLE rule_policy (
  rule_id VARCHAR NOT NULL, version INTEGER NOT NULL, section_id VARCHAR NOT NULL REFERENCES policy_section(section_id),
  PRIMARY KEY (rule_id, version, section_id),
  FOREIGN KEY (rule_id, version) REFERENCES rule_registry(rule_id, version)
);
```

**Acuity and other derived reference values** are computed once at build time from the loaded data and stored on `member` / `ref_hcpcs`, never typed by hand.

## 6. Core entity and claim tables (`core`, in DuckDB)

```sql
CREATE TABLE address (
  address_id     VARCHAR PRIMARY KEY,         -- 'A-000123'
  line1          VARCHAR NOT NULL,            -- synthetic street text
  city           VARCHAR NOT NULL,
  county         VARCHAR NOT NULL,            -- one of 12 synthetic counties
  region         VARCHAR NOT NULL,            -- R1..R3
  zip            VARCHAR NOT NULL,            -- synthetic
  lat DOUBLE NOT NULL, lon DOUBLE NOT NULL,
  is_rural       BOOLEAN NOT NULL,
  building_id    VARCHAR                      -- same value = same physical building (multi-tenant buildings, decoy D2)
);

CREATE TABLE member (
  member_id        VARCHAR PRIMARY KEY,       -- 'M-000123'
  src_key_hash     VARCHAR,                   -- salted SHA-256 of the CMS beneficiary key; NULL for ghost members
  birth_year       SMALLINT NOT NULL,
  sex              VARCHAR NOT NULL,          -- stored for display only; NEVER a model feature
  address_id       VARCHAR NOT NULL REFERENCES address(address_id),
  coverage_start   DATE NOT NULL,
  death_dt         DATE,                      -- assigned by overlay for ~2.5% of members; legitimate claims after it are removed
  acuity_score     DOUBLE NOT NULL            -- 0..1, derived from diagnosis/chronic-condition breadth in the base data
);
-- 'src_key_hash IS NULL' would reveal ghosts, so ghosts get a random-looking hash too; their identity lives in gt only.

CREATE TABLE provider (
  provider_id      VARCHAR PRIMARY KEY,       -- 'P-0042' (individuals and organizations)
  provider_type    VARCHAR NOT NULL,          -- INDIVIDUAL | ORGANIZATION
  name_syn         VARCHAR NOT NULL,
  specialty_code   VARCHAR NOT NULL REFERENCES ref_specialty(specialty_code),
  primary_address_id VARCHAR NOT NULL REFERENCES address(address_id),
  phone            VARCHAR NOT NULL,          -- synthetic; shared values create graph edges
  tin_syn          VARCHAR NOT NULL,
  npi_syn          VARCHAR NOT NULL UNIQUE,   -- synthetic, 'SYN' prefixed so it can never be mistaken for a real NPI
  enroll_dt        DATE NOT NULL,
  status           VARCHAR NOT NULL,          -- ACTIVE | EXCLUDED
  is_sole_provider_county BOOLEAN NOT NULL    -- computed: only provider of this specialty in its county (disruption warning)
);

CREATE TABLE facility (
  facility_id    VARCHAR PRIMARY KEY,         -- 'F-012'
  name_syn       VARCHAR NOT NULL,
  facility_type  VARCHAR NOT NULL,            -- HOSPITAL | CLINIC | DME_WAREHOUSE | LAB | DIALYSIS | IMAGING
  address_id     VARCHAR NOT NULL REFERENCES address(address_id),
  operator_provider_id VARCHAR REFERENCES provider(provider_id)
);

CREATE TABLE provider_facility (
  provider_id VARCHAR NOT NULL REFERENCES provider(provider_id),
  facility_id VARCHAR NOT NULL REFERENCES facility(facility_id),
  role        VARCHAR NOT NULL,               -- PRACTICES_AT | OPERATES | SHIPS_FROM
  start_dt    DATE NOT NULL, end_dt DATE,
  PRIMARY KEY (provider_id, facility_id, start_dt)
);

CREATE TABLE owner (
  owner_id   VARCHAR PRIMARY KEY,             -- 'O-031'
  name_syn   VARCHAR NOT NULL,
  owner_type VARCHAR NOT NULL                 -- PERSON | HOLDING_CO
);

CREATE TABLE ownership (
  ownership_id VARCHAR PRIMARY KEY,
  owner_id     VARCHAR NOT NULL REFERENCES owner(owner_id),
  provider_id  VARCHAR REFERENCES provider(provider_id),
  facility_id  VARCHAR REFERENCES facility(facility_id),
  pct          DOUBLE NOT NULL,               -- 0..100
  is_control   BOOLEAN NOT NULL,              -- pct >= 50
  start_dt     DATE NOT NULL, end_dt DATE,
  CHECK ((provider_id IS NULL) <> (facility_id IS NULL))
);

CREATE TABLE exclusion (                       -- LEIE-shaped, 100% synthetic
  exclusion_id  VARCHAR PRIMARY KEY,
  provider_id   VARCHAR NOT NULL REFERENCES provider(provider_id),
  excl_type     VARCHAR NOT NULL,
  excl_dt       DATE NOT NULL,
  reinstate_dt  DATE
);

CREATE TABLE claim (
  claim_id             VARCHAR PRIMARY KEY,    -- 'C-0001234567', sequential, same format for CMS-derived and injected
  claim_type           VARCHAR NOT NULL,       -- CARRIER | DME | INPATIENT  (open enum)
  member_id            VARCHAR NOT NULL REFERENCES member(member_id),
  billing_provider_id  VARCHAR NOT NULL REFERENCES provider(provider_id),
  rendering_provider_id VARCHAR REFERENCES provider(provider_id),
  referring_provider_id VARCHAR REFERENCES provider(provider_id),
  facility_id          VARCHAR REFERENCES facility(facility_id),
  from_dt              DATE NOT NULL,
  thru_dt              DATE NOT NULL,
  pos_code             VARCHAR REFERENCES ref_place_of_service(pos_code),
  dx1 VARCHAR, dx2 VARCHAR, dx3 VARCHAR,
  paid_amt             DECIMAL(12,2) NOT NULL, -- = sum of line paid amounts (checked)
  CHECK (thru_dt >= from_dt)
);
-- DELIBERATELY ABSENT: any column saying where a claim came from or whether it was injected.
-- Lineage lives only in gt.duckdb and in load_manifest, so no detector or model can read it.

CREATE TABLE claim_line (
  claim_id      VARCHAR NOT NULL REFERENCES claim(claim_id),
  line_no       SMALLINT NOT NULL,
  service_dt    DATE NOT NULL,                 -- date of service for this line
  hcpcs         VARCHAR NOT NULL,              -- joins ref_hcpcs / ref_ncci_ptp / ref_mue (no FK: codes outside ref_hcpcs are tolerated and reported by DQ)
  modifier1     VARCHAR, modifier2 VARCHAR,
  units         INTEGER NOT NULL CHECK (units > 0),
  billed_amt    DECIMAL(12,2),
  allowed_amt   DECIMAL(12,2) NOT NULL,
  paid_amt      DECIMAL(12,2) NOT NULL CHECK (paid_amt >= 0),
  rendering_provider_id VARCHAR REFERENCES provider(provider_id),
  facility_id   VARCHAR REFERENCES facility(facility_id),
  pos_code      VARCHAR REFERENCES ref_place_of_service(pos_code),
  PRIMARY KEY (claim_id, line_no)
);

CREATE TABLE inpatient_stay (
  stay_id       VARCHAR PRIMARY KEY,
  claim_id      VARCHAR NOT NULL REFERENCES claim(claim_id),
  member_id     VARCHAR NOT NULL REFERENCES member(member_id),
  facility_id   VARCHAR NOT NULL REFERENCES facility(facility_id),
  admit_dt      DATE NOT NULL,
  discharge_dt  DATE NOT NULL,
  dx1           VARCHAR
);

CREATE TABLE referral (                          -- derived + pseudo-assigned
  referral_id        VARCHAR PRIMARY KEY,
  from_provider_id   VARCHAR NOT NULL REFERENCES provider(provider_id),
  to_provider_id     VARCHAR NOT NULL REFERENCES provider(provider_id),
  member_id          VARCHAR NOT NULL REFERENCES member(member_id),
  claim_id           VARCHAR REFERENCES claim(claim_id),   -- the claim the referral is attached to
  referral_dt        DATE NOT NULL,
  referral_type      VARCHAR NOT NULL            -- ORDER (DME) | REFERRAL | LAB_ORDER
);
-- Whether a referral was in the source or assigned by us is recorded in gt_referral_origin (gt.duckdb), not here.

CREATE TABLE investigation (                     -- prior outcomes; seeded
  investigation_id VARCHAR PRIMARY KEY,           -- 'INV-0042'
  opened_dt        DATE NOT NULL,
  closed_dt        DATE NOT NULL,
  scheme_type      VARCHAR NOT NULL REFERENCES ref_scheme_type(scheme_type),
  disposition      VARCHAR NOT NULL,              -- CONFIRMED | UNFOUNDED | EDUCATION | INSUFFICIENT
  reason_code      VARCHAR NOT NULL REFERENCES ref_reason_code(reason_code),
  exposure_amt     DECIMAL(12,2) NOT NULL,
  recovered_amt    DECIMAL(12,2) NOT NULL,
  rationale        VARCHAR NOT NULL,              -- 2-3 sentences generated from templates + parameters
  signature_json   VARCHAR NOT NULL,              -- fv_v1 feature vector at opened_dt + rule IDs + graph pattern
  CHECK (closed_dt >= opened_dt)
);
CREATE TABLE investigation_provider (
  investigation_id VARCHAR NOT NULL REFERENCES investigation(investigation_id),
  provider_id      VARCHAR NOT NULL REFERENCES provider(provider_id),
  role             VARCHAR NOT NULL,              -- SUBJECT | NETWORK_MEMBER
  PRIMARY KEY (investigation_id, provider_id)
);

CREATE TABLE load_manifest (
  batch_id VARCHAR PRIMARY KEY, source_name VARCHAR NOT NULL, file_name VARCHAR NOT NULL,
  sha256 VARCHAR NOT NULL, rows BIGINT NOT NULL, adapter_version VARCHAR NOT NULL, loaded_at TIMESTAMP NOT NULL
);
CREATE TABLE gen_manifest (
  run_id VARCHAR PRIMARY KEY, master_seed BIGINT NOT NULL, config_sha256 VARCHAR NOT NULL,
  code_commit VARCHAR, table_hashes_json VARCHAR NOT NULL, created_at TIMESTAMP NOT NULL
);
```

**Constraint note:** declare PKs and FKs in the DDL as the specification. DuckDB's handling of FK checks during bulk loads and later UPDATE/DELETE was not verified for this document. If loading is slow or errors, load first and run `dq/fk_check.sql` instead; the validation is what matters.

## 8. Ground-truth design (`gt.duckdb`)

```sql
CREATE TABLE gt_scheme (
  scheme_id     VARCHAR PRIMARY KEY,           -- 'SCH-DUP-03' (also used for decoys: 'DEC-D1-02')
  kind          VARCHAR NOT NULL,              -- SCHEME | DECOY
  scheme_type   VARCHAR NOT NULL,              -- DUP | UPC | ... | D1..D5
  official_category VARCHAR NOT NULL,
  split         VARCHAR NOT NULL,              -- train | val | test
  difficulty    VARCHAR NOT NULL,              -- EASY | MEDIUM | HARD
  profile       VARCHAR NOT NULL,              -- ESCALATING | STEADY | BURST | CORRECTED  (decoys: STABLE)
  onset_month   SMALLINT NOT NULL,             -- m01..m36
  end_month     SMALLINT,
  params_json   VARCHAR NOT NULL,              -- every random draw, so any instance is reproducible
  sub_seed      BIGINT NOT NULL
);
CREATE TABLE gt_scheme_subject (
  scheme_id VARCHAR NOT NULL REFERENCES gt_scheme(scheme_id),
  entity_type VARCHAR NOT NULL,                -- PROVIDER | MEMBER | OWNER | FACILITY
  entity_id   VARCHAR NOT NULL,
  role        VARCHAR NOT NULL,                -- PRIMARY | PRESCRIBER | RING_MEMBER | GHOST_MEMBER | OWNER ...
  PRIMARY KEY (scheme_id, entity_type, entity_id)
);
CREATE TABLE gt_claim_label (
  claim_id VARCHAR NOT NULL, line_no SMALLINT NOT NULL,
  scheme_id VARCHAR NOT NULL REFERENCES gt_scheme(scheme_id),
  label     VARCHAR NOT NULL,                  -- POSITIVE | DECOY_NEGATIVE | CONTEXT
  role      VARCHAR NOT NULL,                  -- INJECTED_COPY | ORIGINAL | UPCODED | ADDED_COL2 | EXCESS_UNITS | POST_DEATH | DURING_STAY | GHOST | OVERLOAD_DAY | GEO_CONFLICT | EXTRA_VISIT | RING_ORDER ...
  original_value_json VARCHAR,                 -- e.g. {"hcpcs":"99213","paid":86.10} for upcoded lines
  PRIMARY KEY (claim_id, line_no, scheme_id)
);
CREATE TABLE gt_provider_split (provider_id VARCHAR PRIMARY KEY, split VARCHAR NOT NULL);   -- every provider, scheme or not
CREATE TABLE gt_pred_label (
  provider_id VARCHAR NOT NULL, snapshot_dt DATE NOT NULL, horizon_days SMALLINT NOT NULL,
  y TINYINT NOT NULL, future_pos_dollars DOUBLE NOT NULL, prior_pos_dollars DOUBLE NOT NULL,
  split VARCHAR NOT NULL,
  PRIMARY KEY (provider_id, snapshot_dt, horizon_days)
);
CREATE TABLE gt_referral_origin (referral_id VARCHAR PRIMARY KEY, origin VARCHAR NOT NULL);   -- SOURCE | PSEUDO_ASSIGNED | SCHEME
CREATE TABLE gt_member_origin   (member_id VARCHAR PRIMARY KEY, origin VARCHAR NOT NULL);     -- CMS | GHOST
CREATE TABLE gt_claim_origin    (claim_id VARCHAR PRIMARY KEY, origin VARCHAR NOT NULL);      -- CMS | INJECTED | MODIFIED
```

**Label semantics**
- A claim line is **POSITIVE** only if injected or modified by a scheme. Lines that are natural background hits in the CMS data are **unlabelled**, treated as negatives in evaluation, and reported as such: *recall is exact, precision is a lower bound* because a few "false positives" may be genuine anomalies in the base data. State this on the eval page.
- A provider is positive for a window if it has any POSITIVE line in it. A **decoy** provider is negative by design.
- Detectors, the case builder and the brief generator never read `gt.duckdb`. A test enforces it.

## 9. Train / validation / test split

**Principle: split by entity first, then by time, and never reuse test providers for tuning.**

1. **Entity split.** Every provider gets a split from `gt_provider_split`: scheme and decoy instances are assigned to splits in the allocation below, and each instance's providers (including ring members and prescribers) share its split. Remaining normal providers are assigned by seeded hash to roughly 50 / 20 / 30. Ghost members and ghost-scheme claims belong to the scheme's split.
2. **Time layout** (analysis window = 36 months `m01..m36`):

| Period | Use |
|---|---|
| m01–m12 | Clean baseline for peer statistics and training negatives. No scheme starts here |
| m13–m20 | Train/val scheme onsets |
| m22–m30 | **Test scheme onsets** (later, so test is also a temporal hold-out) |
| Prediction snapshots (month ends) | Train and val: m10–m21. **Purge gap m22–m24** (the longest horizon is 90 days). Test: m25–m33 (labels reach m36) |

3. **What each split does**
   - **Train:** fits IsolationForest per peer group (unsupervised, normal providers only if feasible), the three prediction models, and the seed precedents.
   - **Val:** tunes rule thresholds, alert and tier thresholds, queue weights, and model hyper-parameters. Thresholds are written into `rule_registry.params_json` and **frozen** before test is touched.
   - **Test:** reported once per frozen build. Test scheme parameters are drawn from a **shifted distribution** (milder intensity, different code mixes) so the numbers measure generalization, not memorisation of our own generator.
4. **Allocation of scheme instances (36 total; every scheme type appears in test)**

| Scheme | Official category | Instances | train / val / test |
|---|---|---|---|
| DUP | Duplicate billing | 4 | 2 / 1 / 1 |
| UPC | Upcoding | 4 | 2 / 1 / 1 |
| UNB | Unbundling | 4 | 2 / 1 / 1 |
| EXU | Excessive utilization (units over MUE) | 3 | 1 / 1 / 1 |
| UTL | Excessive utilization (visit frequency) | 4 | 2 / 1 / 1 |
| PHA | Phantom services (after death) | 2 | 1 / 0 / 1 |
| PHB | Phantom services (during inpatient stay elsewhere) | 2 | 1 / 0 / 1 |
| PHC | Phantom services (ghost members) | 2 | 1 / 0 / 1 |
| TMA | Impossible timing (daily minutes) | 2 | 1 / 0 / 1 |
| TMB | Impossible timing (same member, distant facilities, same day) | 2 | 1 / 0 / 1 |
| DME | Coordinated network (DME mill + prescribers) | 3 | 1 / 1 / 1 |
| RNG | Coordinated network (shared-owner referral ring) | 2 | 1 / 0 / 1 |
| EXC | Excluded-provider billing | 2 | 1 / 0 / 1 |
| **Total** | | **36** | **17 / 6 / 13** |

5. **Honest limitation:** test has 13 scheme instances, which is too few for tight provider-level statistics. Therefore:
   - the **primary metrics are claim-line recall/precision-lower-bound and dollar coverage** (hundreds of injected lines per type);
   - provider-level numbers carry bootstrap confidence intervals and the counts `n`;
   - the build is cheap to regenerate, so run `make eval-seeds` over five master seeds and report mean ± spread.

| Decoy | What it looks like to a detector | Why it is legitimate | Trigger | Expected human outcome | Seed exception |
|---|---|---|---|---|---|

## 11. Data-generation and injection strategy

### 11.1 Stages
```
0 download (manual)   1 profile   2 adapter → stg_*   3 canonicalize   4 build entities
5 overlay base        6 decoys    7 schemes (+gt)      8 derive tables  9 validate (DQ)
10 publish (DuckDB + Parquet + manifest)     →   features → detectors → cases → serving
```

### 11.2 Profiling (decides the window and sizes)
Profile the staged CMS data and choose, deterministically: `window_end` = last full month whose line volume ≥ 70% of the median monthly volume (this drops a partial final month); `window_start` = `window_end − 36 months` (or the longest available span if shorter, minimum 24). The profiler also reports lines per month, distinct beneficiaries, HCPCS family mix, and daily volume per original NPI.

### 11.3 Provider layer (we define provider identity, because the CMS provider IDs carry no behaviour)
1. Compute each original NPI's dominant HCPCS family; map family → specialty (`ref_specialty`) via a fixed table (use CMS specialty if present and mapped).
2. **Consolidate** original NPIs into ~450 synthetic individual providers and ~50 organizations (DME suppliers, labs, clinics) with a **capacity-aware, deterministic assignment**: within each specialty, original NPIs are assigned to synthetic providers so that no provider's estimated minutes per day exceed a cap (default 10 h) on any day; assignments that would break it spill to a sibling.
3. Why: after re-keying 1:1 the lines per provider-month would be too sparse for peer statistics, and merging naively would create accidental impossible-timing hits. Consolidating deliberately gives us controlled volume.
4. **Rule to adjust:** after profiling, set `n_individual_providers` so the **average lines per provider-month is ≥ 15**. If the profile gives a lower figure, reduce the provider count. The schema is unaffected.

### 11.4 Geography, members, facilities, owners
- **Counties and addresses** are generated from a seeded layout (3 regions × 4 counties; ~25% rural). Each member gets an address near their county centroid (jitter). Each provider gets a practice address; each facility an address. Some addresses share a `building_id` (the D2 buildings and a few benign ones).
- **Member acuity** = normalized breadth of distinct diagnoses (and chronic flags if present).
- **Death dates:** ~2.5% of members get a `death_dt`; legitimate claims after it are deleted from the base.
- **Facilities:** inpatient stays are assigned to the nearest hospital; professional claims with a facility place of service are assigned to a facility in the member's county; office claims use the provider's practice location.
- **Owners:** most providers have a single unrelated owner; some small groups share an owner benignly (ownership alone is not a signal).

### 11.5 Referral layer
Use a source referring/ordering ID if S1 has one. Otherwise assign, deterministically, an **ordering provider for each DME claim** from providers (primary-care-type) who had a visit with the member in the 60 days before, falling back to a seeded choice, and a smaller sample of professional referrals the same way. All such rows are marked `PSEUDO_ASSIGNED` in `gt_referral_origin`.

### 11.6 Injection operations (all deterministic from `sub_seed`; every changed line is recorded in `gt_claim_label`)
Intensity per month = `profile` multiplier × scheme base intensity; profiles: **ESCALATING** (linear ramp from 0.2 to 1.0 over 6–9 months, then sustained), **STEADY** (0.6), **BURST** (1.0 for ~3 months then stops), **CORRECTED** (ramps, then stops 1–2 months after a CONFIRMED/EDUCATION investigation, and may recur later). Mix ≈ 50 / 20 / 15 / 15.

| Scheme | Operation | Hard variants |
|---|---|---|
| **DUP** | Pick the provider's lines in active months; emit copies with a new `claim_id`: V1 exact copy; V2 changed modifier; V3 date of service ±1 day | V2 and V3 are MEDIUM; mild copy rate is HARD |
| **UPC** | For a fraction f(t) of the provider's office E&M lines, replace the code with a higher `em_level` and set paid/allowed to the target code's `reference_allowed` scaled by the original payment ratio | f small (0.1–0.2) is HARD |
| **UNB** | For lines whose code is a Column 1 code in a real, active `ref_ncci_ptp` pair, add a Column 2 line same member/same service date, no modifier for `modifier_ind = 0` or `1` pairs (paid amount sampled from the code's reference) | pairs with `modifier_ind = 1` where the modifier is wrongly omitted are MEDIUM |
| **EXU** | Set `units` above the code's `mue_value` (×1.5–4) on a share of lines | small overages HARD |
| **UTL** | Add extra visit lines for the same members until visits per member per month reach 2–4× the peer median | mild factor HARD |
| **PHA** | Add lines dated after a member's `death_dt` (members with death dates, 1–3 months after) | |
| **PHB** | Add professional lines for a member dated inside an inpatient stay, billed by a provider in a different county | |
| **PHC** | Create ghost members (no CMS source) with a few visits each, billed only by this provider | HARD (no single-claim rule catches it) |
| **TMA** | On K selected days add enough timed visits that `est_minutes` exceeds the daily cap (e.g. > 14 h) | borderline overload MEDIUM |
| **TMB** | For a member, bill the same day at two facilities more than X km apart | |
| **DME** | A new supplier (short tenure) with high-cost DME codes, 90%+ of orders from 1–3 prescribers, members far from the supplier, orders without a qualifying prior visit | prescribers partially legitimate = HARD |
| **RNG** | One owner controls 2 clinics + 1 DME supplier + 1 lab; closed-loop referrals; shared address and phone | partial overlap HARD |
| **EXC** | Provider enters `exclusion` at some date and keeps billing afterwards | |

After each injection, `claim.paid_amt` is recomputed from lines, and IDs are assigned from a single global counter in sorted order so injected and base claims are indistinguishable by format.

### 11.7 Data-quality gates (stage 9; the build fails if any breaks)
FK integrity; `thru_dt ≥ from_dt`; `units > 0`; `paid ≥ 0`; `claim.paid_amt = Σ line paid`; no claim for a member before `coverage_start` or after `death_dt` except in PHA lines; **no normal provider exceeds the daily-minute cap**; no ID or column that reveals lineage in `core`/`ref`/`feat`/`out`; every `rule_policy` section exists; every scheme has at least N labelled lines; seeded rerun hash equality (§12).

## 12. Seeded reproducibility

- **One `master_seed`** in `config/gen.yaml`, committed. Child seeds come from `numpy.random.SeedSequence(master_seed)` spawned by **named component**: `geography`, `consolidation`, `owners`, `referrals`, `decoy:D1:01`, `scheme:DUP:03`, and so on. Adding a new scheme never shifts another component's random stream.
- **Ordering rules:** every list is sorted by a stable key before sampling; IDs come from sorted counters; no reliance on hash-map iteration order; DuckDB inserts are `ORDER BY` primary key.
- **Pinned inputs:** `load_manifest` stores the SHA-256 of every raw file and the NCCI/MUE quarter. A different input hash changes the output hash and is visible.
- **Tests:** build twice and assert equal Parquet hashes in `gen_manifest.table_hashes_json`; one scheme-level test regenerates a single instance from `gt_scheme.params_json` and `sub_seed` and checks its labelled lines are identical.
- **Seeds for evaluation:** `make eval-seeds` runs 5 master seeds; the demo uses a fixed one (`make reset-demo` restores its snapshot).

## 17. How the data supports 30/60/90-day prediction

- **Snapshots:** provider × month end. **Features** come only from rows dated ≤ snapshot (`feat_provider_month` as-of; alert counts by family over 90/180 days; investigation history with `closed_dt ≤ snapshot`).
- **Label definition (`gt_pred_label`)**, per horizon *h* in {30, 60, 90}:
  `y = 1` iff the provider has POSITIVE injected dollars in `(t, t+h]` **and** either had POSITIVE injected dollars in `(t−180d, t]` (**repeat**) or that future daily dollar rate is ≥ 1.25× the rate in `(t−90d, t]` (**escalation**). Otherwise `y = 0`.
- **Why the data can support it:** schemes have a ramp, so early low-intensity months provide the "prior activity" that precedes escalation. `BURST` and `CORRECTED` providers stop, giving hard negatives that look risky. Decoys and heavy-alert normal providers are negatives that look alike. Providers with prior CONFIRMED investigations that recur are repeat examples.
- **Rough training volume:** hundreds of positive provider-snapshot rows per horizon, which is enough for a shallow gradient-boosting model or logistic regression; report confidence intervals, not point claims.
- **Split:** entity + time as in §9, with the purge gap. Models never see `gt_*` features; only the label comes from `gt_pred_label`.

## 19. How the data supports the Second Brain precedent loop

**Seed history.** About 100 investigations, generated from the actual train/val behaviour so their signatures are consistent with what the detectors really see:
- ~17–20 on **train/val scheme providers** (CONFIRMED or EDUCATION) opened 1–3 months after onset;
- ~9 on **train/val decoys** (UNFOUNDED with `LEGIT_*` reason codes, the knowledge that later drives exceptions);
- ~70 **noise** investigations on providers with the highest natural background-alert scores at the time (mostly UNFOUNDED, some EDUCATION or INSUFFICIENT), so "weak signal ≠ confirmed" is also in the knowledge base.
Test-split providers have **no** seeded investigations, so test cases are scored using precedents from other providers only.

**As-of rule.** A precedent can inform a case only if `closed_dt ≤` the case's as-of date. The retrieval query enforces it, and a test checks it.

**Precedent.** One per investigation at seed time (`source='SEED'`), and one per case closed in the live system (`source='LIVE'`). Fields: scheme type, disposition, reason code, specialty, rule IDs, graph pattern, and the `fv_v1` feature vector (12 normalized features, fixed order, versioned):
`z_em_high, z_lines_per_member, dup_line_rate, ptp_hit_rate, mue_exceed_rate, z_mean_member_km, referral_top3_share, shared_infra_degree, tenure_months_norm, log_dollars, n_alert_families, acuity_mean`.

**Retrieval.** Structural filter (scheme type, specialty, rule IDs) then cosine similarity on the vector → top-k precedents with similarity, disposition and rationale, which enter the evidence pack as cited items.

**Exception rules** (`wf_exception_rule`, columns: `exc_id`, `version`, `scope_json`, `condition_json`, `effect`, `source_precedent_id` FK, `status`, `simulate_report_json`, `proposed_by`, `approved_by`, `approved_at`, `supersedes`):
- `status` lifecycle: `DRAFT → SIMULATED → APPROVED | REJECTED → RETIRED`.
- The condition is a **list of `{field, op, value}`** over a fixed catalogue of feature names, never code. `effect ∈ {DOWNGRADE_TO_MONITOR, SUPPRESS_ALERT}`.
- **`/simulate`** returns: alerts suppressed, providers affected, dollars no longer reviewed, **conflicts with CONFIRMED precedents**, and (demo environment only, via `gt.duckdb`) **POSITIVE lines that would be lost**. Label that last number "synthetic-ground-truth backtest; a real deployment would use confirmed precedents instead."
- **Live demo:** a D1 case in the test split is rejected as `LEGIT_CLINICAL_PATTERN` → a draft exception is created from the matching seed precedent (PRC-0057 style) → simulate → governance approves → re-run → alerts for the D1 provider drop to Monitor and the next case cites `EXC-0002` and `PRC-0057`. EXC-0001 (the D2 building) is already approved, so the first screen already shows an exception citation.

## Final recommended schema (one-paragraph summary)

**`claims.duckdb`** holds `ref_*`, `policy_section`, `rule_registry`, `rule_policy`, the core entities (`address`, `member`, `provider`, `facility`, `provider_facility`, `owner`, `ownership`, `exclusion`), claims (`claim`, `claim_line`, `inpatient_stay`, `referral`), history (`investigation`, `investigation_provider`), features (`feat_provider_month`, `feat_provider_day`, `feat_graph_edge`), detector output (`alert`, `alert_line`, `case*`, `evidence_pack`, `prediction`, `eval_metric`) and manifests. **`gt.duckdb`** holds the ground truth and is invisible to detectors. **`app.db`** holds the `serving_*` copies and the `wf_*` workflow, precedent, exception and audit tables. Everything is built from one seed, split by entity and time, and checked by data-quality gates before any detector runs.
